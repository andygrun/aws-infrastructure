https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html

Configured AWS CLI with IAM Identity Center:

```bash
aws configure sso
```

Configured an SSO session and created a local CLI profile named:

```text
admin
```

Logged in:

```bash
aws sso login --profile admin
```

Verified the authenticated AWS identity:

```bash
aws sts get-caller-identity --profile admin
```

### What I learned

The AWS CLI profile name is a **local configuration name**. It does not have to match the name of the AWS/IAM Identity Center user.

For example:

```bash
--profile admin
```

tells the AWS CLI to use the credentials/configuration stored under the local `admin` profile.

## 6. Terraform AWS Provider

Configured the AWS provider using the official HashiCorp AWS provider documentation:

https://registry.terraform.io/providers/hashicorp/aws/latest/docs

The initial provider uses:

* Region: `eu-west-1`
* AWS CLI profile: `admin`

```hcl
provider "aws" {
  region  = "eu-west-1"
  profile = "admin"
}
```

### Why `profile = "admin"`?

Terraform uses the AWS provider to communicate with AWS.

The `profile` tells Terraform to use the AWS CLI credentials/configuration stored under the local `admin` profile.

This means Terraform does not need AWS access keys written directly into the Terraform configuration.

## 9. AWS Regions

The infrastructure and IAM Identity Center are currently in different AWS regions:

| Purpose             | Region       |
| ------------------- | ------------ |
| Infrastructure      | `eu-west-1`  |
| IAM Identity Center | `eu-north-1` |

`eu-west-1` will be used for the infrastructure labs, including resources such as VPC, EC2, S3, CloudWatch and SNS.

IAM Identity Center is currently configured in `eu-north-1`.

Because of this, Terraform uses a second AWS provider configuration with an alias:

```hcl
provider "aws" {
  region  = "eu-north-1"
  profile = "admin"
  alias   = "sso"
}
```

The `sso` alias allows Terraform resources that belong to IAM Identity Center to explicitly use the `eu-north-1` provider while the normal infrastructure resources continue using `eu-west-1`.

## 10. IAM Identity Center Discovery with Terraform

First verified the IAM Identity Center instance using the AWS CLI:

```bash
aws sso-admin list-instances --profile admin --region eu-north-1
```

This confirmed that there is currently one IAM Identity Center instance in `eu-north-1`.

Instead of hardcoding the Instance ARN and Identity Store ID into Terraform, used the Terraform `aws_ssoadmin_instances` data source to retrieve the existing Identity Center information dynamically.

Configured the aliased provider:

```hcl
provider "aws" {
  alias   = "sso"
  region  = "eu-north-1"
  profile = "admin"
}
```

Then added:

```hcl
data "aws_ssoadmin_instances" "this" {
  provider = aws.sso
}
```

### What I learned

A Terraform **resource** is used to create and manage infrastructure.

A Terraform **data source** is used to look up information about infrastructure that already exists.

The `provider = aws.sso` argument tells this data source to use the aliased `sso` provider, rather than the default `eu-west-1` provider.

The `arns` and `identity_store_ids` attributes returned by the data source are sets. Sets are unordered collections, so they cannot be accessed directly using an index.

Because AWS currently has exactly one Identity Center instance, converted the set to a list and selected its first element:

```hcl
tolist(data.aws_ssoadmin_instances.this.arns)[0]
```

and:

```hcl
tolist(data.aws_ssoadmin_instances.this.identity_store_ids)[0]
```

The `[0]` approach is appropriate for the current environment because the AWS CLI confirmed that there is only one Identity Center instance.

### Terraform outputs

Added outputs to expose the discovered values:

```hcl
output "arn" {
  value = tolist(data.aws_ssoadmin_instances.this.arns)[0]
}

output "identity_store_id" {
  value = tolist(data.aws_ssoadmin_instances.this.identity_store_ids)[0]
}
```

Initially, `terraform output` returned:

```text
Warning: No outputs found
```

This happened because the output values had not yet been recorded in Terraform state.

Ran:

```bash
terraform apply -auto-approve
```

Then:

```bash
terraform output
```

This displayed the discovered Identity Center values.

Used:

```bash
terraform show
```

to inspect the resulting Terraform state.

### Important distinction

`terraform plan` previews what Terraform intends to do.

`terraform apply` actually applies the configuration and updates Terraform state.

`terraform output` reads output values from Terraform state.


## 11. Git Workflow and Terraform State

Before committing the changes, checked the repository:

```bash
git status
git diff
```

This showed the modified Terraform configuration and an untracked `terraform.tfstate` file.

Learned that Terraform state should not be committed to the repository.

Updated `.gitignore`:

```gitignore
.terraform/
*.tfstate
*.tfstate.*
```

Used:

```bash
terraform fmt
```

to format the Terraform configuration.

Used:

```bash
git diff
```

to review the changes before committing.

Used:

```bash
git diff --check
```

to check the diff for common whitespace errors.

Committed and pushed the changes:

```bash
git add .
git commit -m "Add Terraform SSO data source and outputs"
git push
```

Verified the repository was clean with:

```bash
git status
```

### What I learned

`git diff` shows changes in the working directory compared with the last commit.

`git diff --staged` can be used to review changes that have already been added to the staging area.

Terraform state is separate from the Terraform configuration. The configuration describes the desired setup, while the state records information Terraform needs to track and manage that setup.
